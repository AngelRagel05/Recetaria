# Flujo Git supervisado de Recetaria

Aplica esta skill a todo cambio realizado por un agente, junto con las skills SDD que correspondan. Es un contrato de instrucciones supervisadas, no una garantía de comportamiento probado. Gestiona Git; no aprueba especificaciones, planes, implementaciones ni verificaciones. Usa comandos Git ordinarios, sin scripts, hooks, dependencias, ampliaciones de CI, operaciones forzadas ni automatismos sobre `main`. El desarrollador puede trabajar con su propio flujo.

`start`, `adopt`, `commit`, `push`, `switch-dev`, `merge`, `publish-dev`, `close` y `cancel` son fases de esta conversación, no comandos ejecutables. Mantén una sola tarea activa por repositorio. Una autorización Git nunca se deduce de la solicitud de una tarea, de un estado SDD, de `PASS`, de `MEMORY.md` ni de un permiso anterior.

## Estado y autorizaciones

- La fuente técnica de tarea activa son exactamente las claves de configuración Git **local** `recetaria.active-branch` y `recetaria.base-commit`. Lee ambas con `git config --local --get-all`; cada una debe tener exactamente un valor o ninguna debe existir. Si falta una, hay duplicados o el valor no concuerda con Git, detente y consulta. No repares ni sobrescribas por inferencia. `MEMORY.md` solo informa del foco.
- La base es el commit de `dev` desde el que nació o se adoptó la rama. Obtén el remoto con `git config --get branch.dev.remote` y exige `branch.dev.merge = refs/heads/dev`. No supongas `origin` ni aceptes un upstream distinto para la rama de trabajo. Consulta la punta remota con `git ls-remote --exit-code --heads <remoto> dev` y compara su SHA con `git rev-parse dev` y la base cuando corresponda. No uses `fetch` para estas comprobaciones: modifica referencias locales. Si el remoto no se puede consultar, detén la acción afectada.
- Antes de **cada acción lógica que cambie estado** (`start`, cada `push`, cada `commit`, `switch-dev`, `merge`, `publish-dev`, `close`, `adopt` o `cancel`), muestra referencias, rutas, commits y efectos concretos que correspondan; pide un permiso **específico y posterior** a esa propuesta. La autorización cubre una sola acción inmediata y sus preparativos necesarios, pero no la siguiente acción. Se consume al intentarla o si cambian sus condiciones; no persiste entre reintentos ni sesiones. Las comprobaciones de solo lectura no necesitan permiso.
- Antes de una operación, verifica que no haya un merge, rebase, cherry-pick, revert o bisect incompleto. Si lo hay, detente para una decisión; no uses `reset`, `rebase`, `stash`, `pull` ni borrados forzados como recuperación automática.
- Las puertas SDD se prueban con los estados vigentes de `spec.md`, `plan.md` y `tasks.md`, `MEMORY.md`, Git y la conversación actual. Si falta evidencia de una aprobación humana o revisión exigible, pídela o repite la revisión. Cualquier cambio funcional posterior a las verificaciones invalida sus resultados y `test_reviewer`. Solo el cierre administrativo previsto de estados SDD y `MEMORY.md` conserva la verificación anterior y exige revisión documental y `git diff --check` propios. Un `PASS` no autoriza un commit ni ninguna otra acción Git.

## `start`: rama nueva y primer push

1. Tras la solicitud de una tarea, exige que las dos claves locales estén ausentes, que `git branch --show-current` sea `dev` y que índice y árbol estén limpios, incluidos archivos no seguidos. Comprueba que no haya operaciones Git incompletas.
2. Resuelve el remoto de `dev`, consulta su punta con `git ls-remote --exit-code --heads <remoto> dev` y exige que coincida con `git rev-parse dev`. Si no coincide o la consulta falla, informa y detente; nunca sincronices mediante fetch, pull, merge o rebase automáticos.
3. Forma `<tipo>/<slug>` con `feat`, `fix`, `refactor`, `docs`, `test` o `chore` y un slug que cumpla `^[a-z0-9]+(-[a-z0-9]+)*$`. Comprueba con `git show-ref` y `git ls-remote --heads <remoto>` que no exista local ni remotamente.
4. Presenta tipo, nombre técnico, rama exacta, base y efecto de registrar la tarea. **Solicita autorización específica** antes de `git switch -c <rama> dev` y de registrar, en configuración Git local, un único `recetaria.active-branch=<rama>` y `recetaria.base-commit=<SHA de dev>`. Creación y registro son una sola acción autorizada. Si una escritura falla, detente y muestra el estado parcial para intervención; no empieces a modificar archivos.
5. Muestra rama, remoto y destino exactos, y pide **otro permiso** para el push inicial. Comprueba otra vez que no haya upstream ni rama remota; solo tras autorizarlo ejecuta `git push -u <remoto> <rama>`. Esta es la única excepción al requisito de upstream previo. Un rechazo o fallo conserva rama y registro; no modifiques archivos hasta que el push termine bien. Cada reintento necesita un permiso nuevo.

## `adopt` y `cancel`

- `adopt` solo procede sin estado local de tarea activa, desde una rama de nombre válido distinta de `dev` y `main`, sin operación Git incompleta y con upstream exacto `<remoto>/<misma-rama>` y rama remota existente comprobada con `git ls-remote --heads`. Puede conservar cambios sin commit de una tarea cancelada. Calcula `git merge-base --all dev <rama>`: exige exactamente una base. Comprueba `dev`, su punta remota y esa base, y muestra cualquier deriva sin resolverla. Presenta rama, upstream, SHA base y efecto del registro; **solicita autorización explícita** antes de registrar ambas claves. La deriva continúa bloqueando verificación final y merge.
- `cancel` requiere autorización explícita propia. Presenta la tarea, las dos claves que retirará y el trabajo que conservará. Tras el permiso, retira únicamente ambas claves de Git config local con `git config --local --unset-all` y confirma que desaparecieron. Conserva rama local, remota, commits, índice y árbol; cancelar no integra ni cierra una tarea publicada. Si la retirada queda parcial, bloquea tareas nuevas y consulta.

## `commit` y `push` de la rama

- `commit`: exige estar en la rama activa, upstream exacto, índice inicialmente vacío, selección no vacía de rutas **literales** y ausencia de operación Git incompleta. Acepta solo `<tipo>: <descripción en español>` en una línea, con uno de los seis tipos de trabajo y descripción no vacía; `merge:` no es un tipo de trabajo. Revisa la selección para excluir cambios ajenos y secretos. Muestra mensaje y lista exacta de rutas; tras permiso específico, prepara solo esas rutas con `git add -- <rutas>`, comprueba que el índice contiene únicamente lo autorizado y ejecuta `git commit -m <mensaje>`. No hagas push implícito. Si falla después de preparar, conserva el árbol e informa del estado del índice; retirar rutas con `git restore --staged` es otra acción que requiere propuesta y autorización nuevas. Todo reintento exige un permiso nuevo.
- `push` inicial pendiente: si `start` terminó antes de publicar, incluso en otra sesión, permite reanudarlo desde la rama activa registrada solo si conserva la base, no tiene upstream ni homónima remota, no hay operaciones incompletas y el índice y árbol siguen limpios. Vuelve a comprobar `dev` y su remoto frente a la base, muestra el destino y pide un **nuevo permiso** antes de `git push -u <remoto> <rama>`. No modifiques archivos hasta que termine bien; si la rama remota ya existe o la base derivó, detente y consulta.
- `push` de trabajo posterior: exige rama activa, upstream exacto `<remoto>/<rama>`, ninguna operación incompleta y destino idéntico a ese upstream. Consulta la punta remota real con `git ls-remote --exit-code --heads <remoto> <rama>` y muestra remoto, destino y **todos** los commits locales pendientes de esa punta; detente si las historias divergen o no puedes consultar el remoto. Tras permiso específico, ejecuta `git push <remoto> <rama>` sin forzar. Puede publicar varios commits locales previamente autorizados. Si Git rechaza el push, conserva los commits y pide otro permiso para reintentar; no integres cambios ajenos automáticamente. Rechaza `main`, otras ramas y destinos.

## Deriva, `switch-dev`, `merge` y `publish-dev`

- Antes de la verificación final, antes de proponer `switch-dev`, inmediatamente antes de proponer y ejecutar `merge`, y antes de `publish-dev`, compara base registrada, `dev` local y punta remota real mediante `git ls-remote`. Si cualquiera difiere o el remoto no se puede consultar, detente, explica los SHA disponibles y consulta; no actualices ni integres nada automáticamente.
- `switch-dev` exige verificaciones vigentes, ningún `BLOCKED`, árbol e índice limpios, upstream exacto y punta remota de trabajo igual a la local. Presenta origen, destino `dev` y efecto; solicita **permiso específico** para `git switch dev`. Después confirma que la rama actual es `dev` y que `HEAD` sigue en la base registrada. Si el cambio o la validación falla, detente sin merge ni reparación automática. Un reintento necesita otra autorización.
- `merge` es una acción distinta. Desde `dev` validada, vuelve a comparar la base con `dev` local y remoto **antes de proponerlo**; muestra origen, destino `dev`, `--no-ff` y `merge: integra <rama> en dev`. Solicita **otro permiso** y, justo antes de ejecutar, vuelve a consultar el remoto y confirmar que todo sigue igual, incluidos la punta publicada de trabajo, árbol e índice limpios y verificaciones vigentes. Solo entonces ejecuta `git merge --no-ff <rama> -m "merge: integra <rama> en dev"`. Si la comprobación falla, el permiso no sirve para un reintento. Si hay conflictos, conserva el estado, informa y pide autorización nueva para cualquier recuperación: no ejecutes `merge --abort` ni cambies de rama automáticamente. Las correcciones posteriores invalidan la verificación anterior.
- `publish-dev` no está cubierto por el merge. Comprueba que `HEAD` sea el merge esperado: primer padre igual a la base y segundo padre igual a la punta publicada de la rama activa. Consulta `dev` remoto y exige que siga en la base; repite la consulta inmediatamente antes del push. Muestra remoto, destino y commit de merge pendiente; solicita **otro permiso** para `git push <remoto> dev` sin forzar. Si falla o el remoto avanzó, conserva el merge local y la tarea activa, no cierres y consulta. Un reintento necesita otro permiso.

## `close` y cierre del CI

- Solo desde `dev`, tras comprobar que el push de `dev` terminó bien y que su punta remota es el merge esperado que contiene la punta de trabajo, presenta rama activa y los valores de ambas claves locales. Solicita **permiso específico de cierre** para retirar únicamente `recetaria.active-branch` y `recetaria.base-commit` con `git config --local --unset-all`. Confirma que desaparecieron. Conserva las ramas local y remota sin borrarlas; si el registro queda parcial, bloquea tareas nuevas y consulta. Un reintento necesita otro permiso.
- Después de publicar `dev` y observar su CI, registra el resultado externo real en `MEMORY.md` mediante una **nueva tarea y rama `docs/`** sometida a todo este flujo y conservada tras su cierre. El CI provocado por ese cierre documental no reabre la tarea funcional. Si el CI aún no se ha observado, conserva el pendiente en `MEMORY.md`.
