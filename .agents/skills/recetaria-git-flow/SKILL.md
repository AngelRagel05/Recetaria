# Flujo Git local supervisado de Recetaria

Aplica esta skill a todo cambio realizado por un agente, junto con las skills SDD que correspondan. Es un contrato de instrucciones supervisadas, no una garantía de comportamiento probado. Gestiona Git; no aprueba especificaciones, planes, implementaciones ni verificaciones. Usa comandos Git ordinarios, sin scripts, hooks, dependencias, ampliaciones de CI, operaciones forzadas ni automatismos sobre `main`. El desarrollador puede trabajar con su propio flujo y se encarga de publicar e integrar las ramas.

`start`, `adopt`, `commit`, `final-commit` y `cancel` son fases de esta conversación, no comandos ejecutables. Mantén una sola tarea activa por repositorio. Una autorización Git nunca se deduce de la solicitud de una tarea, de un estado SDD, de `PASS`, de `MEMORY.md` ni de un permiso anterior.

## Estado y autorizaciones

- La fuente técnica de tarea activa son exactamente las claves de configuración Git **local** `recetaria.active-branch` y `recetaria.base-commit`. Lee ambas con `git config --local --get-all`; cada una debe tener exactamente un valor o ninguna debe existir. Si falta una, hay duplicados o el valor no concuerda con Git, detente y consulta. No repares ni sobrescribas por inferencia. `MEMORY.md` solo informa del foco.
- La base es el commit de `dev` desde el que nació o se adoptó la rama. Obtén el remoto con `git config --get branch.dev.remote` y exige `branch.dev.merge = refs/heads/dev`. No supongas `origin` ni exijas upstream para la rama de trabajo. Consulta la punta remota con `git ls-remote --exit-code --heads <remoto> dev`; para `start`, debe coincidir con `git rev-parse dev`. No uses `fetch` para estas comprobaciones: modifica referencias locales. Si la consulta inicial falla, no crees la rama.
- Antes de **cada acción lógica que cambie estado** (`start`, cada `commit`, `final-commit`, `adopt` o `cancel`), muestra referencias, rutas, commits y efectos concretos que correspondan; pide un permiso **específico y posterior** a esa propuesta. La autorización cubre una sola acción inmediata y sus preparativos necesarios, pero no la siguiente acción. Se consume al intentarla o si cambian sus condiciones; no persiste entre reintentos ni sesiones. Las comprobaciones de solo lectura no necesitan permiso.
- Antes de una operación, verifica que no haya un merge, rebase, cherry-pick, revert o bisect incompleto. Si lo hay, detente para una decisión; no uses `reset`, `rebase`, `stash`, `pull` ni borrados forzados como recuperación automática.
- Las puertas SDD se prueban con los estados vigentes de `spec.md`, `plan.md` y `tasks.md`, `MEMORY.md`, Git y la conversación actual. Si falta evidencia de una aprobación humana o revisión exigible, pídela o repite la revisión. Cualquier cambio funcional posterior a las verificaciones invalida sus resultados y `test_reviewer`. Solo el cierre administrativo previsto de estados SDD y `MEMORY.md` conserva la verificación anterior y exige revisión documental y `git diff --check` propios. Un `PASS` no autoriza un commit ni ninguna otra acción Git.

## `start`: rama local nueva

1. Tras la solicitud de una tarea, exige que las dos claves locales estén ausentes, que `git branch --show-current` sea `dev` y que índice y árbol estén limpios, incluidos archivos no seguidos. Comprueba que no haya operaciones Git incompletas.
2. Resuelve el remoto de `dev`, consulta su punta con `git ls-remote --exit-code --heads <remoto> dev` y exige que coincida con `git rev-parse dev`. Si no coincide o la consulta falla, informa y detente; nunca sincronices mediante fetch, pull, merge o rebase automáticos.
3. Forma `<tipo>/<slug>` con `feat`, `fix`, `refactor`, `docs`, `test` o `chore` y un slug que cumpla `^[a-z0-9]+(-[a-z0-9]+)*$`. Comprueba con `git show-ref` y `git ls-remote --heads <remoto>` que no exista local ni remotamente.
4. Presenta tipo, nombre técnico, rama exacta, base y efecto de registrar la tarea. **Solicita autorización específica** antes de `git switch -c <rama> dev` y de registrar, en configuración Git local, un único `recetaria.active-branch=<rama>` y `recetaria.base-commit=<SHA de dev>`. Creación y registro son una sola acción autorizada. Si una escritura falla, detente y muestra el estado parcial para intervención; no empieces a modificar archivos.
5. Tras confirmar que la rama y las dos claves coinciden, continúa el trabajo local conforme a las puertas SDD. No publiques inicialmente la rama ni exijas upstream para modificar archivos.

## `adopt` y `cancel`

- `adopt` solo procede sin estado local de tarea activa, desde una rama local de nombre válido distinta de `dev` y `main` y sin operación Git incompleta. Puede conservar cambios sin commit de una tarea cancelada. Calcula `git merge-base --all dev <rama>` y exige exactamente una base. Comprueba `dev` y su punta remota cuando sea consultable; informa de cualquier deriva sin resolverla. Presenta rama, SHA base y efecto del registro; **solicita autorización explícita** antes de registrar ambas claves. No exige upstream ni existencia remota.
- `cancel` requiere autorización explícita propia. Presenta la tarea, las dos claves que retirará y el trabajo que conservará. Tras el permiso, retira únicamente ambas claves de Git config local con `git config --local --unset-all` y confirma que desaparecieron. Conserva la rama local, sus commits, índice y árbol, y cualquier rama remota que ya exista. Si la retirada queda parcial, bloquea tareas nuevas y consulta.

## `commit` y `final-commit`

- `commit`: exige estar en la rama activa, índice inicialmente vacío, selección no vacía de rutas **literales** y ausencia de operación Git incompleta. Acepta solo `<tipo>: <descripción en español>` en una línea, con uno de los seis tipos de trabajo y descripción no vacía; `merge:` no es un tipo de trabajo del agente. Revisa la selección para excluir cambios ajenos y secretos. Muestra mensaje y lista exacta de rutas; tras permiso específico, prepara solo esas rutas con `git add -- <rutas>`, comprueba que el índice contiene únicamente lo autorizado y ejecuta `git commit -m <mensaje>`. Se permiten varios commits locales. Si falla después de preparar, conserva el árbol e informa del estado del índice; retirar rutas con `git restore --staged` es otra acción que requiere propuesta y autorización nuevas. Todo reintento exige un permiso nuevo.
- `final-commit`: cumple las mismas precondiciones, y además requiere verificaciones aplicables vigentes y `test_reviewer` sin `BLOCKED` para una tarea SDD. Identifica expresamente el último commit antes de mostrar mensaje, rutas y efecto de liberar el registro. Solicita un permiso propio para preparar esas rutas, confirmar el índice, crear el commit y, **solo si Git confirma su éxito**, retirar ambas claves con `git config --local --unset-all`. Confirma la ausencia de ambas; permanece en la rama de trabajo y conserva rama, árbol y commits. Si falla el commit, conserva las claves e informa del índice. Si falla la retirada, informa del estado parcial, bloquea tareas nuevas y pide una autorización nueva para recuperar el registro; no repara ni reintenta implícitamente.

## Deriva y seguimiento externo

- Después de `start`, si `dev` local o su punta remota avanzan respecto de la base, informa de los SHA conocidos y continúa en la rama local sin alterar la base. Si la consulta remota falla, informa de esa incertidumbre; no afirmes que hay sincronización. La publicación, integración y resolución de conflictos corresponden al desarrollador. El agente no hace push, no cambia a `dev`, no hace merge ni borra ramas como parte de este flujo. No sincroniza ni repara con `fetch`, `pull`, `rebase`, `reset`, `stash` u operaciones forzadas.
- Tras la publicación e integración manuales y después de observar el CI, registra su resultado real en `MEMORY.md` mediante una **nueva tarea y rama `docs/`** sometida a este mismo flujo local. Si el CI aún no se ha observado, conserva el pendiente. El CI generado por ese cierre documental no reabre la tarea funcional.
